> 评估基准：仓库现状（`src/` 19 个模块，14,991 行；`config.js` / `db.js` / `state.js` / `llm.js` / `dialogue.js` 已读）

## 二、硬伤 1：两层叙事控制是冗余，不是玩法

文档同时引入了两套"决定接下来发生什么"的机制：

```
Layer 3  Director（AI）     →  决定 beat：offer / event / encounter / silence
Layer 2  人生阶段系统        →  决定 stage：少年 / 而立 / 不惑 / 知天命
```

**问题：这两层谁听谁的？**

- 如果 Director 可以绕过 stage 推商品 → stage 的 `categories` 限制形同虚设
- 如果 stage 限制 Director → Director 的"自由创造"（§零的核心卖点）被腰斩

文档没给答案。而现状是：**代码里根本没有"年龄"这个概念。** 我全局检索过，`src/` 里没有任何 `age` 字段、没有生辰、没有岁时。现在只有：

```
remainingDays   剩余天数（就是货币本身）
categorySpent   各分类累计消费（→ 解锁传奇、触发 3 次里程碑抉择）
```

所以引入 `age` 的代价是：

1. 160 件商品全部要挂年龄门（`ageGate`），否则"少年买下梦中公寓"不成立
2. 结算、墓志铭 prompt、人生回放（`replay.js`）、成就（`state.js`）全部要多一个维度
3. 里程碑抉择现在挂在**消费额**上（1500 / 8000 / 15000），要改成挂在**年龄**上——或者两套并存（更糟）

**换来的玩法增量是多少？**

零。玩家操作依然是"买 → 扣天数 → 买"。变的只是商品的标签和文案。

> 文档自己的话："年龄不是时间的函数，是'消费结构'的函数。"
>
> 这句话是对的，而且很聪明。**但它的正确实现是一个纯函数，不是一个系统。**

```js
// 30 行，不需要 Stage 系统，不需要新状态字段
export function inferAge(categorySpent, remainingDays) {
  const spent = Object.values(categorySpent).reduce((a, b) => a + b, 0);
  const funRatio  = (categorySpent.fun + categorySpent.consume) / (spent || 1);
  const workRatio = (categorySpent.career + categorySpent.cognition) / (spent || 1);
  const cashRatio = (categorySpent.health + categorySpent.family) / (spent || 1);
  // 贪玩 → 时间飞逝；忙碌 → 时间变慢；养生 → 延缓
  const pace = 0.6 + funRatio * 1.2 - workRatio * 0.5 - cashRatio * 0.4;
  return Math.max(0, Math.floor((30000 - remainingDays) / 400 * pace));
}
```

**建议：把 Layer 2 从"系统"降级为"一个派生函数 + 一组阶段文案"。** 输出给 AI 用（进 prompt），输出给 UI 用（年龄显示），但不成为独立的状态机。

## 三、硬伤 2：线索系统是全篇唯一不可替代的东西，却被排到 v0.6

先说清楚为什么它最值钱：

| 特性 | 固定脚本能做到？ | 需要 AI 做数值决策？ |
|---|---|---|
| 多世界换皮 | 能（就是写多份文案） | 不需要 |
| 商品 AI 生成 | 能（就是写多个模板） | 不需要 |
| **线索回响** | **不能** | **不需要** |
| 导演决策 | 半能（计时器+状态机） | 名义上需要 |

线索系统是**唯一一个"固定脚本做不到、但也不需要 AI 碰数值"**的机制。这意味着：

- 情感回报最高（"二十年前你没买那把伞"）
- 落地风险最低（纯状态记录 + 一次文本生成）
- 完全符合你的铁律（AI 挂掉 → 用本地模板生成一句"回响"）

**而且它现在就能从已有机制派生出来，零新机制：**

```js
// 你已有的东西 → 线索
// 1. 奇遇里选了 A 没选 B  → 打开线索 "那条你没走的路"
// 2. 里程碑抉择选了"深耕优势" → 打开线索 "被你放弃的短板，会在什么时候回来"
// 3. 摸鱼被吐槽的那件事       → 打开线索 "那次浪费的 300 天"
// 4. 「只是看看」没买的那件商品 → 打开线索 "你犹豫过的东西"
```

看第 4 条——**这正好就是文档 §3.2B 里的"只是看看"选项。** 一个 UI 小改，直接喂给线索系统。

**建议：把线索系统从 v0.6 提到 v0.3 第一个做。** 它是"AI 当引擎"这个论点的**唯一实证**——如果这一件做出来效果好，再谈扩展；如果不好，你会省下 90% 的工作量。

## 四、硬伤 3：成本模型算术错，且漏掉了最大的那一项

### 4.1 算术

文档说单局 ~100K token（这个量级大致对），但结论"~¥0.03"不对。按当前主流 OpenAI 兼容端点（DeepSeek 档）粗算，100K 混合输入输出大约 **¥0.2 ~ 0.4/局**，不是 ¥0.03。

不过——**这不是重点。BYOK 模式下，成本不是你的，是用户的。**

重点是下面这个，文档一个字没提：

### 4.2 默认预算只够玩 2 局

`src/llm.js:19`：

```js
export const BUDGET_PRESETS = [50000, 200000, 1000000];
```

当前默认档位 200,000 token。而你的核心长线玩法是**跨局**的：

> "🔁 轮回与人生清单：每局结束获得轮回积分（RP），跨世收集 160 段人生"

**160 件商品要跨很多局才能收齐。** 如果每局吃掉 100K，默认预算 20 万 = **两局就用完**。用户第三次开游戏就会弹出"额度用完"的面板——正好在轮回机制开始产生粘性的时候。

**建议：**

1. 要么把默认预设改成 `[1M, 5M, 20M]` 并重写文案（"这些额度大约可以玩 N 局"）
2. 要么把单局 token 预算硬性压到 30K 以内（见下一节的方案）

### 4.3 真正该担心的不是钱，是延迟感知

15 分钟一局，平均每次交互间隔不到 10 秒。文档 §5.3 要求"导演决策必须隐形"，这个判断是对的——**但 25 秒一次的 tick 恰恰做不到隐形**，因为它会在玩家正在阅读商品描述、正在犹豫的时候发起请求并可能弹出一个 beat。

**建议：导演 tick 必须挂在"玩家操作的空隙"上，而不是固定时钟。** 触发条件应该是"上一次 beat 结束 + 玩家已连续 N 次操作 + 无未决弹窗"，而不是 `setInterval(25s)`。

### 4.4 漏掉的最大负债：离线导演

`§5.2 手段 2` 写：

```ts
// 代码直接决定 30% 的 silence，不调 AI
if (Math.random() < 0.3 && this.lastBeat !== 'silence') { ... }
```

**这一行已经承认了问题**：只要代码能"直接决定"一个 beat，那它就能决定全部 beat。所谓"AI 当引擎"，实际是"代码当引擎，AI 偶尔插手"——与 §零的核心论点自相矛盾。

而铁律要求你必须有离线路径，所以你必须写一个**本地导演**。写完本地导演之后你会发现：**它已经够好了，AI 导演只是让它稍微更懂你一点。**

这个结论不是反对你的方案，而是**给你的方案指出正确的形态**。

## 五、四、五节的代码不能直接用（逐条）

§4.2 和 §4.3 是草图，不是可运行代码。至少 4 处问题：

| 位置 | 问题 |
|---|---|
| `class Director` | 没有 constructor，`this.state` / `this.referee` 全是 `undefined`，`tick()` 一调就崩 |
| `referee.validate` | `this.lastBeat` 在 referee 对象上不存在（lastBeat 挂在 Director 上）→ 判断恒为 `false`，**"不允许连续两次相同 beat"这条校验形同虚设** |
| `referee.validate` | 引用了 `world.allowedPolarities`，但 `world` 既没 import 也没定义 → `ReferenceError` |
| `referee.clampEffect` | `Math.floor(state.lifespan * 0.05)` —— 但你的状态字段叫 `remainingDays`，不叫 `lifespan`。**这暴露了一个真问题：新架构的字段命名与现有代码是两套。**

第 4 条最值得注意：整份文档用的字段名（`remainingDays` vs `lifespan`、`categorySpent` vs 无、`world` / `player` / `threads`）**与 `state.js` 里的 `createInitialGameState` 不是一套**。这说明方案是"从零想象"的，不是"在现有代码上长出来的"。

这不是能力问题——但落地时会造成一次大重构。**建议：写这类方案时，把字段名全部对齐现有 `GAME_STATE`，把成本核算从"想象"换成"读代码"。**

## 七、我的优化版：把"AI 当引擎"切成三层

**核心原则：AI 只能决定"叫什么名字、说什么话、想起了什么"。数值、时机、合法性一律代码决定。**

| 层 | 谁决定 | 具体内容 |
|---|---|---|
| **数值 / 时机** | **代码** | 商品何时出现、价格区间、扣多少天、事件极性、结局类型、年龄增长 |
| **内容 / 语气** | **AI** | 商品的名字与描述、NPC 台词、事件的具体情节、回响的那一句话 |
| **记忆 / 连续性** | **代码存，AI 读** | 线索表由代码维护（`open` / `resolved` / `lastTouched`），AI 只负责"在这一刻把它讲出来" |

**这个切法的三个收益：**

1. **导演决策不需要 API。** 用现有的事件间隔计时器（`randomEventIntervalSeconds: 100`）+ 一个 15 行的节奏状态机，就能产出 `offer / event / encounter / silence` 序列。零成本、零延迟、离线完整。
2. **AI 从"引擎"变成"引擎上的渲染层"。** 每次调用仍有明确降级路径，铁律零风险。
3. **世界观变成真正纯数据。** 一个世界 = 一份 i18n 字典 + `CATEGORY_META` + `GRADE_META` + 主题色 + 事件池。**这才是"每个世界一个 PR"的正确形态——会写小说的人只需填一个 key → 文本的表。**

### 7.1 导演的本地形态（可直接落地）

不要 AI 决定 beat，用**节奏表 + 排除规则**：

```js
// 纯代码导演：零 API、零延迟、离线完整。AI 只负责把内容写好看。
const RHYTHM = [
  { afterOps: 1,  beat: 'offer'      },   // 开局必然有东西可买
  { afterOps: 3,  beat: 'silence'    },   // 别急，让人喘口气
  { afterOps: 5,  beat: 'encounter'  },   // 有人上门
  { afterOps: 8,  beat: 'event'      },   // 世界发生点什么
  { afterOps: 10, beat: 'reflection' },   // 停下来想想
];

export function nextBeat(state) {
  const ops = state.opsSinceLastBeat;
  // 排除规则（就是文档 §2.4 想表达的东西，但代码说了算）
  if (state.pendingAdventure || state._adventurePaused) return 'silence';
  if (state.lastBeat === 'event' && state.recentNegative) return 'reflection';
  // 有未完结线索且超过 N 次交互没碰 → 优先回响
  const stale = state.threads.find(t => t.status === 'open' && ops - t.touchedAt > 4);
  if (stale) return 'echo';              // ← 新增 beat，专门给线索系统用
  const row = RHYTHM.find(r => r.afterOps > ops);
  return row ? row.beat : 'silence';
}
```

注意最后我**加了一个 `echo` beat**——文档把回响写成了 `event` 的一种，但它在机制上完全不同（它必须命中一条已有线索，而不是生成新事件）。**给它一个独立的 beat 类型，代码才管得住它。**

### 7.2 线索系统的 schema（补全文档的 `NarrativeThread`）

文档的 `NarrativeThread` 缺了三个关键字段——**没有它们，回响就是随机的**：

```js
{
  id, seed, openedAt, lastTouchedAt, status, weight,   // 文档已有
  echoCandidate: string,   // ← 缺：一句可回响的"素材"，回响时喂给 AI
  source: 'adventure' | 'milestone' | 'skipped' | 'roast',  // ← 缺：来源决定何时该回响
  echoCount: 0,            // ← 缺：回响过几次（防止同一个梗反复出现）
}
```

`source: 'skipped'` 就是「只是看看」——**这是最便宜的线索来源，也是情感冲击最强的**（"你当时没买"）。

## 十、一句话总结

> 你这一版的真正进步是**把 AI 的位置从"外包"提到了"引擎"**。
> 但它还没回答那个更难的问题：**当引擎熄火时，车还能不能开？**
>
> 答案是：**能。只要你把"引擎"拆成"规则 = 代码，叙事 = AI"。**
